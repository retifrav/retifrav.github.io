Meilisearch on a Hugo-based website

2026-10-21 16:36:48 +0200
38 min read

Some years ago I added a basic search to my website. It was rather crude and even primitive, but it was better than nothing. I did want to use a proper search engine already back then, but the variety of available solutions wasn’t overwhelming, and none looked attractive enough to invest some effort into. As years passed by, more search engines became available, and out of the new ones I’ve now settled with Meilisearch.

It extended the search functionality on my website with very useful features such as actually searching the entire contents, ranking the results, ability to exclude certain keywords and some more. At the same time, I did not get rid of the previous search implementation either, it is still available and works as a fallback.

Why basic search isn’t enough

The disadvantages of my current (now previous) implementation were very clear from the start:

  • can only find what’s inside index.json, meaning that the entire website contents need to be there, and the more content you have, the bigger index.json is (and it is fetched on every search requests), which is why I had to reduce it to just summaries of pages, which naturally meant that nothing else was searchable;
  • no ranking/ordering of the search results, so any match has the same “weight” as others;
  • if the search query contains more than one keyword, it will only find places where those words are placed strictly next to each other (with no other words between them).

What does Meilisearch have

Being a proper search engine, Meilisearch works with indexed content, and for me that alone was already the biggest win (as my summaries-only search was borderline useless). But there is more:

  • full-text search by keywords but also semantic search or a combination of the two (haven’t tried that yet);
  • prefix search (or partial matches, which I kinda had already), exact matches, negative search, stop words and dictionaries;
  • ranking, which is configurable too;
  • typo tolerance, also configurable;
  • embedders or so-called vector-search;
  • MCP integration for LLM agents;
  • some more features that I have not read about yet.

Hell, the search got so advanced that I had to write a guide for how to use it.

Alternatives

There are several other search engines available, out of which I was also considering the following:

  • Typesense - seems to be the next best thing after Meilisearch, or maybe even a better one, but apparently it keeps everything in RAM, of which I don’t have a lot on the VPS where my website is hosted, so that sounded concerning. Also, by the looks of it, the setup/configuration appeared to be more involved;
  • Elasticsearch/OpenSearch - fucking Java again, and right from the start it requires more than 1 GB of RAM (recommended 8 GB!), so hell no. Other than that, Elasticsearch is actually what I was looking at already all those years ago;
  • Pagefind - this one looks like a (much) better alternative to my current basic search, and as I understand it might be possible to use it “offline” too (self-contained bundles / documentation packages).

If you are brave enough to try cloud-based solutions without self-hosting options, then there are even more alternatives out there, but I didn’t look at those at all.

Meilisearch as the main search

Architecture

To reiterate, this is how the so-to-say “architecture” of my basic search looked like up until now:

In order to add a search engine into that, specifically Meilisearch, one would need to do the following:

  1. Set up the Meilisearch instance to run somewhere, probably on the same server where the website is hosted;
  2. Index the website content in the format that Meilisearch understands and save it in Meilisearch database;
    • Hugo can help with that via custom output format/layout, but you will still need to create a special indexing script for creating search index records out of that output;
    • Both Hugo and the indexing script need to be executed somewhere by someone, which implies having CI/CD (already present in my current setup) for running those tasks (unless you hate yourself and do all that manually);
  3. Implement the searching functionality on your website - sending requests to the Meilisearch instance and showing results to the user;
    • Everything can be done with JavaScript, so there is still no need to involve a backend, and your website remains to be a collection of static HTML pages generated by Hugo;
    • Optionally implement a simpler fallback search (conveniently, that I already have with my basic search).
  4. Since it isn’t a good idea to expose Meilisearch port to the wild internet (especially that there will be an API key involved), you should probably reverse-proxy search requests with your current web-server (the very same NGINX that serves the website itself).

So then the architecture diagram changes accordingly:

And as far as my understanding goes, replacing Meilisearch with a different engine shouldn’t cause me a lot of troubles, because they all(?) likely share the same general idea. Of course, the indexing script will require certain engine-specific adjustments, but other than that it does not feel like I am getting myself vendor-locked to Meilisearch.

Installation and configuration

Meilisearch itself is a single self-contained executable, and there is also a pre-made Docker image for running it in a container, so the installation procedure is rather uncomplicated.

Docker container

The container will be running from a non-root ubuntu user with a rootless Docker, so check whether that user has lingering enabled:

$ loginctl show-user ubuntu -p Linger
Linger=yes

The compose file is in /home/ubuntu/meili/compose.yaml:

name: meilisearch

services:
  meilisearch:
    image: getmeili/meilisearch:v1.54.3
    container_name: meilisearch
    restart: unless-stopped
    ports: ["127.0.0.1:7700:7700"]
    env_file: ./meili.env
    environment:
      MEILI_ENV: production
      MEILI_NO_ANALYTICS: "true"
    volumes: ["meili_data:/meili_data"]

volumes:
  meili_data:

The /home/ubuntu/meili/meili.env (chmod 600) contains MEILI_MASTER_KEY - a random secret value:

MEILI_MASTER_KEY=ANY-RANDOM-16-SYMBOLS-STRING-HERE-OR-LONGER

Next thing to note is that I decided to use a named volume for the data persistence, but it should also work fine with a bind mount. Also there is no need to set the timezone for container, as the image has no tzdata out of the box and operates in UTC.

As for analytics/telemetry, in general I wouldn’t mind sharing anonymized data, especially for a product that I got to use free of charge, but Meilisearch collects a tremendous amount of data with no option to select what to share (like how it is done in Home Assistant), so I disabled it.

The 7700 port is not exposed to the internet (binds to localhost), as only the web-server (NGINX) needs to communicate with it (reverse-proxy the search requests).

Creating a container is the usual:

# if you are root now, use the non-root user shell
$ machinectl shell ubuntu@

# that should expand to /home/ubuntu/meili/
$ cd ~/meili/
$ docker compose up -d

And for updating the container image, pin the new version in ./compose.yaml and then:

$ docker compose pull && docker compose up -d

To verify that everything was set up correctly:

# a helper variable
$ M=http://127.0.0.1:7700

$ curl -s "$M/health" -w "\n"
{"status":"available"}

# this should return 401, which means that authentication is enforced
$ curl -s -o /dev/null -w '%{http_code}\n' "$M/keys"
401

# the port should only be available from localhost
$ ss -ltn | grep 7700
LISTEN 0      4096       127.0.0.1:7700      0.0.0.0:*

$ docker compose logs meilisearch | grep -i -E 'environment|telemetry'
meilisearch  | Environment:        "production"
meilisearch  | Anonymous telemetry:    "Disabled"

API keys

Using Meilisearch API requires certain API keys to be created, a minimum set of two:

  1. Indexing/writing key - for creating search indexes;
  2. Searching/reading key - for performing the actual search.

Actually, once the master key is set, Meilisearch seems to create some default keys itself, but I still prefer to issue my own keys with an explicit scope. I should probably delete the defaults ones too.

The keys are created by sending requests to Meilisearch API using MEILI_MASTER_KEY (the one from /home/ubuntu/meili/meili.env). Aside from those minimally required two keys, later you might need to create some more, so here’s a convenience function for issuing a new key:

# assuming you are still in that non-root user shell
$ cd ~/meili/

# load MEILI_MASTER_KEY without typing it, so it won't get saved in commands history
$ set -a; . ./meili.env; set +a

# that helper variable again
$ M=http://127.0.0.1:7700

# a convenience function for issuing API keys
$ mkkey() { curl -s -X POST "$M/keys" \
    -H "Authorization: Bearer $MEILI_MASTER_KEY" \
    -H 'Content-Type: application/json' --data "$1" \
    | python -c 'import json,sys; r=json.load(sys.stdin); print(r.get("key") or r)'
}

# check that it is a function
$ type mkkey
mkkey is a function
Indexing key

First is the index writing key:

$ mkkey '{"name":"YOUR-WEBSITE-indexer","description":"Indexing/writing key for the indexing step over SSH","actions":["indexes.create","indexes.delete","indexes.get","indexes.swap","settings.update","documents.add","tasks.get"],"indexes":["*"],"expiresAt":null}'
ISSUED-API-KEY-FOR-INDEXING

This key is meant to be used for creating index records in Meilisearch with the indexing script, and in my setup that script is run via SSH by a CI/CD build agent, for which I have a separate user account on the server where the website is hosted. So I put that key into /home/buildbot/YOUR-WEBSITE-index-writer.key file:

$ echo 'ISSUED-API-KEY-FOR-INDEXING' \
    | sudo -u buildbot tee /home/buildbot/YOUR-WEBSITE-index-writer.key > /dev/null
$ sudo chmod 600 /home/buildbot/YOUR-WEBSITE-index-writer.key

…although you should probably do this differently for the same reason of keeping the key out of commands history.

Searching key

Second is the search-only reading key:

$ mkkey '{"name":"YOUR-WEBSITE-search","description":"Searching/reading key for querying /api/search","actions":["search"],"indexes":["*"],"expiresAt":null}'
ISSUED-API-KEY-FOR-SEARCHING

This key goes into NGINX config for the website, something like /etc/nginx/sites-enabled/YOUR-WEBSITE:

# ...

location = /api/search/indexes/INDEX-NAME/search {
    limit_except POST { deny all; }
    
    # up to 20 requests above the rate are let through right away
    # (instead of being delayed, which would make search-as-you-type lag),
    # anything more gets 429
    #limit_req zone=YOUR-WEBSITE_search burst=20 nodelay;
    #limit_req_status 429;
    
    client_max_body_size 4k;
    proxy_pass http://127.0.0.1:7700/indexes/INDEX-NAME/search;
    proxy_set_header Authorization "Bearer ISSUED-API-KEY-FOR-SEARCHING";
}
location /api/search/ {
    return 404;
}

location / {
    try_files $uri $uri/ =404;
}

# ...

For the rate limiting to work you will also need to add the following inside http { ... } block in the main /etc/nginx/nginx.conf:

# rate limiting
limit_req_zone $binary_remote_addr zone=YOUR-WEBSITE_search:10m rate=10r/s;

…and then uncomment the limit_req lines in the website config.

Either way, once NGINX is restarted, you should be able to test the requests proxying by running this from any other host:

$ curl -s -X POST https://YOUR-WEBSITE/api/search/indexes/INDEX-NAME/search \
    -H 'Content-Type: application/json' \
    --data '{"q":"ololo"}' -w "\n" \
    | jq
{
  "message": "Index `INDEX-NAME` not found.",
  "code": "index_not_found",
  "type": "invalid_request",
  "link": "https://docs.meilisearch.com/errors#index_not_found"
}

The index not being found is an expected result, since nothing has been indexed yet, so this only verifies that Meilisearch endpoint is reachable and that NGINX does the proxying. And if the API key for searching was incorrect, then the response would be this instead:

{
  "message": "The provided API key is invalid.",
  "code": "invalid_api_key",
  "type": "auth",
  "link": "https://docs.meilisearch.com/errors#invalid_api_key"
}
The keys UIDs

The API keys are identified by UIDs, which are random version-4 UUID values generated during the key creation. You can generate a UID beforehand yourself (with uuidgen -r) and pass it to mkkey function as a part of the JSON payload (there will be an example a bit later), but it is probably better/easier to just get the auto-generated values after the keys have been created/issued:

$ curl -s "$M/keys" -H "Authorization: Bearer $MEILI_MASTER_KEY" \
    | jq '.results[] | {name, uid, actions, indexes}'
{
  "name": "YOUR-WEBSITE-indexer",
  "uid": "INDEXER-KEY-UID-HERE",
  "actions": [
    "indexes.create",
    "indexes.delete",
    "indexes.get",
    "indexes.swap",
    "settings.update",
    "documents.add",
    "tasks.get"
  ],
  "indexes": [
    "*"
  ]
}
{
  "name": "YOUR-WEBSITE-search",
  "uid": "SEARCH-KEY-UID-HERE",
  "actions": [
    "search"
  ],
  "indexes": [
    "*"
  ]
}
{
  "...": "..."
}

It is not very important to know/save those UIDs, but it does matter for reproducibility. An API key value is derived from UID and master key (MEILI_MASTER_KEY), and the same master key and the same UID will produce the same API key value. This means that you will be able to recreate the exact same API keys after losing/deleting the Meilisearch database, so you won’t need to update the keys saved in /home/buildbot/YOUR-WEBSITE-index-writer.key, or in the NGINX config, or in your LLM agent or wherever else you might be calling the Meilisearch API from.

When/if it will come to a point of re-creating an existing API key in a fresh Meilisearch instance, you’ll just need to add the UID value to the issuing command:

$ mkkey '{"uid":"SEARCH-KEY-UID-HERE","name":"YOUR-WEBSITE-search","...":"..."}'
ISSUED-API-KEY-FOR-SEARCHING

and it will produce the same API key value as the one you already have in your configs or wherever.

So, aside from saving the MEILI_MASTER_KEY in a password manager / secrets storage, it is also recommended to save the keys UIDs. Those are less secret, and you can probably even store them in plain text somewhere (documentation, wiki, etc).

Hugo integration

New custom output and updated layout

Hugo can help with the indexing task via a custom output - same idea as how it is done with index.json, but more advanced now. The output format will be described in .../layouts/_default/index.searchrecords.json:

{{- /*
    Source for the Meilisearch index. Covers every listed page with content (pages with
    `build: list: never` are not in `site.Pages`).
*/ -}}
{{- if not site.Params.search.index -}}
    {{- errorf "The SearchRecords output format is enabled, but params.search.index (the Meilisearch index uid) is not set" -}}
{{- end -}}
{{- $pages := slice -}}
{{- range where site.Pages "Kind" "in" (slice "home" "section" "page") -}}
    {{- $content := .Content -}}
    {{- if strings.TrimSpace (plainify $content) -}}
        {{- $breadcrumbs := slice -}}
        {{- range .Ancestors.Reverse -}}
            {{- if not .IsHome -}}
                {{- $breadcrumbs = $breadcrumbs | append .Title -}}
            {{- end -}}
        {{- end -}}
        {{- $pages = $pages | append (dict
            "path" .RelPermalink
            "title" .Title
            "section" .Section
            "date" (cond .Date.IsZero "" (.Date.Format "2006-01-02"))
            "breadcrumbs" $breadcrumbs
            "tags" (.Params.tags | default .Params.newstags | default slice)
            "content" $content
        ) -}}
    {{- end -}}
{{- end -}}
{{- jsonify (dict "noHTMLEscape" true) (dict
    "format" 1
    "index" (string site.Params.search.index)
    "pages" $pages
) -}}

As you can see, it takes the .Content part, which is the rendered HTML body without layout parts around it (navigation, header, footer, etc). I do realize that it might seem counter-intuitive to index the rendered HTML instead of the original Markdown files, but actually the rendered content is a more reliable source for building a search index:

  • HTML parsing is a more or less common task with existing standard implementations (such as html.parser in Python), but processing Markdown the same way as Hugo does it would mean reimplementing Hugo’s renderer (with shortcodes too) to produce the matching output;
    • code listings might originate from Markdown fences (three backticks) or from highlight shortcode, and a non-Hugo parser could process a # comment line inside a highlight block as a <h1> heading;
    • search results link to the sections on pages via anchors that Hugo assigned to the headings, so an indexer working with raw Markdown files would need to know how Hugo does it in order to produce matching IDs;
    • there are likely more caveats like this, no point in listing all of them;
  • unparsed/unprocessed Markdown would bring its own syntax into the index (and so into the search results) - the bold/italic/etc markup, bracketed links, front matter, shortcodes (which would not get evaluated, by the way, as noted in the first point) and so on - all that would need to be converted into the plain text;
  • I have raw HTML inclusions in my Markdown sources (some tables and other custom-styled things), and that HTML needs to get stripped before indexing, so I would still need to do some pre-processing for my raw Markdown files anyway.

To enable the new output, config.toml gets this:

[params.search]
    # where the search requests go (NGINX forwards this to Meilisearch),
    # and an empty value here means using only the basic index.json search
    endpoint = "/api/search/"
    # Meilisearch index name
    index = "INDEX-NAME"

# ...

[outputs]
    # - `HTML` - the actual website contents
    # - `RSS` - RSS feeds, duh
    # - `JSON` - basic/fallback search (index.json)
    # - `SearchRecords` - Meilisearch index source (search-records.json)
    home = ["HTML", "RSS", "JSON", "SearchRecords"]

[outputFormats.SearchRecords]
    mediaType = "application/json"
    baseName = "search-records"
    isPlainText = true
    notAlternative = true

and .../layouts/_default/baseof.html gets the following:

{{- with .Site.Params.search.endpoint }}
    <!-- using Meilisearch (with a fallback to basic index.json search without these) -->
    <meta name="searchEndpoint" content="{{ . }}">
    <meta name="searchIndex" content="{{ $.Site.Params.search.index }}">
{{- end }}

Getting a bit more advanced, the INDEX-NAME might not be a forever static value. In my simple case it is indeed a static value because I have only one revision of my website contents - the latest. But for scenarios where you might need to have an index per content revision (such as for documentation in different versions of your SDK/library/etc) the index name might have a dynamic format like SDK_DOCUMENTATION_123, so it would get updated on every new published revision (SDK_DOCUMENTATION_124, SDK_DOCUMENTATION_125 and so on), and every indexing run would create a new Meilisearch index (while in my case I just swap old with new, so there is only ever one). In such a case of several live indexes, trying to search for things within v1.2.4 documentation will get you results from the index that was created for this exact version and not from v1.2.3 or v1.2.5 - and that is mainly the point of stating the index name in the searchIndex meta tag.

Updated search.js

My crude search function has changed quite a lot, but in short what it does now is first it tries to send a query to Meilisearch, and if that fails, then it fallbacks to the basic search (which got some small improvements too).

There are several interesting implementation details in the updated script, such as utilizing AbortController for cancelled search queries and using search “generations” to drop no longer relevant (superseded) results, but it is probably better if you inspect the full script yourself instead of me posting 300+ lines here. The version that I had when I was writing this article is saved separately here, but you can also get the latest version directly from the live website.

Later addition of the page field

One problem I didn’t immediately notice was that trying to search for “conan” keyword showed me results for just one article, but I knew that Conan is for sure mentioned in at least one more article. The reason turned out to be the fact that default ranking favors title matches, and all the “conan” matches from the Conan article (68 in total) outranked “conan” matches from other articles, and since search results get cut off at 50 limit, matches from other articles (as well as remaining 18 matches from the Conan article) were discarded.

To account for this I needed to:

  1. Add a filterable page field to the index (that should happen in the indexing script);
  2. Send two requests in parallel (with Promise.all()) in search.js:
    • one is to get the best section of each page (which pages will get listed and in what order);
    • and another is the current top-50 query.

That way super long articles with 50+ matches for a search keyword should no longer “evict” other articles matches from the search results.

But that was not the end of it, as a bit later I noticed that some of the search results listed sections that had nothing to do with the search query. That turned out to be the same title matching problem but from a different point: that second top-50 request was searching in page titles too, so every section of that article was getting a match in its title, and since a match in the title outranks everything else, it didn’t matter that the some sections were also a match in their heading and text, because all the sections of that article were getting the same rank and with the same original order of how they go on the page. And since I made it so that only 3 sections per page are shown in the results, those sections were getting discarded too.

So now the search goes like this:

  1. That second top-50 request searches only in the sections headings and text;
  2. The best section of a page from the first request gets listed first, but only if the search query matched in that section itself, not just in the page title. That is still needed for queries where some of the words are only in the page title, because without the titles the second request wouldn’t find the sections that have only the rest of the words (by default Meilisearch drops words from the end of the query), while for the first request that is exactly the best section of the page;
  3. If a page matched only in its title, it gets listed without any sections.

A short summary at this point would be that implementing a proper search functionality on a website is fekkin not trivial at all - I had to update my searching script at least 3 times already, while it’s been only a couple of days since the deployment.

Indexing script

So yes, there needs to be something that would index your website content, as Meilisearch itself does not fetch or crawl anything (unless you are using their cloud variant), so data will get into Meilisearch instance only when a script or some other executable will call the API to create an index. Moreover, Meilisearch operates with asynchronous tasks, and to know their status one would also need to poll the API. But even before calling the API, search-records.json file needs to be split into documents, while also splitting long articles into sections/chunks and trying not to tear code blocks into unrelated pieces.

I figured that all of that can be done by a Python script, which I named simply index-for-search.py. Same as with the search.js, I won’t post the entire 600+ lines of it in the article - you can get the full script from here. Also, not gonna lie, I didn’t exactly write it myself, if you know what I mean.

The script is meant to be run by CI/CD build agent over SSH right after the website content (Hugo output) is deployed to server:

$ ssh -o BatchMode=yes -o StrictHostKeyChecking=accept-new buildbot@YOUR-HOST \
    "python - --records /var/www/YOUR-WEBSITE/search-records.json --key-file /home/buildbot/YOUR-WEBSITE-index-writer.key && rm /var/www/YOUR-WEBSITE/search-records.json" \
    < ./scripts/index-for-search.py

If you are going to use TeamCity for that, it would need to be a regular Command Line step (not SSH Exec), and it will also require adding SSH agent build feature with the SSH key for buildbot@YOUR-HOST.

Deleting search-records.json after indexing is optional, and you might even prefer to keep it in case you’ll ever need to re-build the index without running the entire CI/CD chain, but you should be aware that this file is likely to end up being publicly available at https://YOUR-WEBSITE/search-records.json.

    | jq

Basic search as a fallback

As I mentioned, the basic search didn’t go anywhere, and it now serves as a fallback when the main search becomes unavailable for some reason (Meilisearch instance is down, NGINX rate-limiting kicked in, etc).

The implementation is in the same search.js, and even though it got some small improvements (mostly fixes for old problems, such as escaping regular expressions, so these no longer work), it doesn’t do anything new - still a very unintelligent match() for titles and summaries of the articles, so about 95% of the website content is unsearchable, as I have already explained over there.

It does print a warning into web-browser console when the fallback happens:

Meilisearch search is not available (404, no details), falling back to the basic search

Another nice feature of Meilisearch is an MCP server, which you can add to your LLM agent(s). This feature is also disabled by default, so you need to enable it first:

Large MCP responses

So it did connect, and also the tools worked when I tried some queries/prompts, but I noticed the following warning in the output:

Large MCP response (~10.4k tokens), this can fill up context quickly

When I asked Claude about that, he ran some tests and told me that the instructions text from that server/discover response is somewhat sub-optimal. Here are some of the issues he reported:

  • There’s no way to fetch one chunk by ID. That pushes clients to request full text up front, and it’s why I needed a made-up query just to get the missing parts. A get-document tool, or making fields filterable, would fix that;
  • The server’s instructions to clients don’t mention keeping results small. They only say which tools to call in which order. One sentence recommending excerpts and small limits would steer every client toward lean queries;
  • describeIndex returns only 5 sample hits, not the index settings. A client can’t tell which fields support filtering, or whether semantic search is available.

I don’t know why default Meilisearch MCP instructions for clients are so “not optimized” out of the box, maybe because they can’t account for all the ways people could be indexing their content? Besides, my indexing script is probably doing something “unconventional”, so that might have contributed too.

Either way, since there seems to be no way to configure the instructions text, what one can do is overwrite it in NGINX (with sub_filter), since we are already proxying the MCP requests:

# Meilisearch MCP
location = /api/search/mcp {
    # ...

    proxy_pass http://127.0.0.1:7700/mcp;

    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_read_timeout 300s;

    proxy_set_header Accept-Encoding "";  # Meilisearch compresses with br/gzip when asked, and sub_filter cannot read compressed bodies
    sub_filter_types application/json;    # the default is text/html only
    sub_filter_once on;                   # each pattern occurs once per response

    # server/discover
    sub_filter '"instructions":"Meilisearch is a prefix search engine that supports filtering, sorting, federated searching (mixing results from different indexes).Meilisearch support classic keyword search but may also support semantic search throught the use of the hybrid search parameter.\\n                You can find more information about available embedders for a given index when describing an index.We recommend you to use the listIndexes, describeIndex, and searchInIndexes tools, in this order to fetch the right informations from the available indexes."'
               '"instructions":"Search over the YOUR-WEBSITE. It has one index, INDEX-NAME, so skip listIndexes; skip describeIndex as well, because it returns 5 full sample documents (about 6 KB) and no settings. Each document is one section of a page (a long section is split into several chunks): url (page path plus the #anchor of the section; a page intro has no anchor), page_title, hierarchy (heading path), breadcrumbs, section, date, tags, chunk and content. Searchable: content, hierarchy, page_title. Filterable: section (blog, news, etc, projects; the /about/ page has an empty section, which section IS EMPTY matches), tags (about 95, such as cpp, cmake, qt, linux, macos, windows, web, dotnet, home-automation, norway; facetSearch with facetName tags lists them all) and url (=, IN and STARTS WITH; CONTAINS is disabled). Sortable: chunk only. date can be neither filtered nor sorted, but an empty q returns documents newest first, and url STARTS WITH \'/blog/2022/\' or \'/news/2022/05/\' narrows by date. There are no embedders, so hybrid fails, and a search never returns more than 1000 hits. Content is in English and Russian: 88 of 234 blog posts (nearly all from 2014-2018, film reviews among them, so a Latin page_title does not mean English content), all 104 news posts (Russian translations of Norwegian news from 2022) and 17 of 29 etc pages are Russian, so for broad recall send an English and a Russian query in one federated request. Hits are large, so follow the size advice in the searchInIndexes description."';

    # tools/list - searchInIndexes, insert the INDEX-NAME recipe after the first sentence and keep the rest
    sub_filter '"description":"Run multiple search queries in a single API request.'
               '"description":"Run multiple search queries in a single API request. On INDEX-NAME a hit carries about 1200 characters of content on average and up to 7400, so the default limit of 20 returns about 30 KB. For a first pass set attributesToRetrieve to [url, page_title], attributesToCrop to [content], cropLength to 30 and limit to 10 or below (about 5 KB); do not also list content in attributesToRetrieve, or each hit carries it twice. With federation, put limit in federation instead of in the queries. Hits sharing a url are chunks of one section: get them in order with an empty q, filter url = \'<url>\' and sort chunk:asc. To read several sections in one call, use an empty q, filter url IN [\'<url1>\', \'<url2>\'] and no sort; sections of one page come back in reading order whatever the list order. For a whole page in reading order use an empty q, filter url STARTS WITH \'<page url without #anchor>\' and no sort, because sorting by chunk interleaves the sections; a page has up to 100 sections in 160 records and 300 KB, so list the outline first with attributesToRetrieve [url, hierarchy, chunk] and limit 200 (up to about 30 KB).';

    # tools/list - describeIndex, replace the misleading description
    sub_filter '"description":"Describes an index to understand what\'s stored inside and what\'s its purpose."'
               '"description":"Returns only 5 full sample documents (about 6 KB): no settings, no embedders, no field list. On INDEX-NAME skip it; the server instructions already list the fields and settings."';
}

Clearly, these are not universal, as they work only for my particular website, so you would need to come up with the ones specific to yours.

One other shortcoming of these rewrites is that in newer Meilisearch versions the instructions text can be different, so the rewrites would need to be updated. They will also need to be updated if you’ll change your indexing procedure (like it happened here), or you will start adding new documents incrementally instead of swapping the entire index, or maybe you will change the way splitting works, etc. In short, it is fair to say that sub_filter approach is quite fragile.

Anyway, you can verify whether the rewrites are working or not with a request like:

$ curl -s --compressed https://YOUR-WEBSITE/api/search/mcp \
    -H 'Accept-Encoding: gzip, br' \
    -H 'Authorization: Bearer ISSUED-API-KEY-FOR-MCP' \
    -H 'Content-Type: application/json' \
    -H 'MCP-Protocol-Version: 2026-07-28' \
    --data '{"jsonrpc":"2.0","id":1,"method":"server/discover","params":{}}' \
    -w "\n" | jq -r .result.instructions

✻ Crunched for 1m 0s

Looking at the MCP queries, here’s how the search went:

  1. First it executed 4 searches for piracy, пиратство, пиратский торрент and pirated torrent multi-language keywords in one request and used federation to merge results from all of those searches into a single ranked list. The data it selected to fetch was url, page_title and cropped content;
    • dunno why it decided to associate torrent/торрент keywords with piracy, no idea whatsoever;
  2. Then it sent requests with empty search query, just filtering by tags and URLs and without fetching the content at all;
  3. And then it finally fetched the full uncropped content from the narrowed down 9 articles: first from the 4 that got classified as “opinion-focused” and then from the remaining 5, using just the url IN filter for both queries.

Searching in more than one language (so both in english and russian), grouping several search queries in one request and merging the results, not fetching the full article/post/page content right away (so getting cropped content first) - all of that happened thanks to the updated instructions text, otherwise the agent likely would have spent a larger amount of tokens and probably would have missed some content too (especially the parts in russian).

I say, that is pretty cool, even on such a basic level of integration (I haven’t yet touched more advanced features such as semantic/hybrid search, conversations, embedders and so on).
